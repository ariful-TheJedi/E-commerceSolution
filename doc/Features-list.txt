-------------------------------------------------------------------------------
HOW TO USE
-------------------------------------------------------------------------------
1. Developer lists modules and their features (chat, or edits this file).
2. Agent writes them here under MODULES — status starts as [ ].
3. One active module at a time. One feature / use case per turn.
4. Mark status as work moves (agent MUST flip these in the same turn
   as the work — also mirror in AGENTS.md):

       [ ]  planned
       [~]  in progress
       [x]  done
       [-]  parked / deferred

5. Each module has a Progress checklist (require → skeleton → wall →
   features). Flip those boxes when that stage finishes.
6. Each module has modules/<name>/docs/. When the module changes,
   the agent updates those docs in the same turn (brief, folder
   structure, database, api).
7. Do not start the next module until the current one's list is done
   (or the developer parks remaining items).

### 1. Product
Schema:   product
Folder:   modules/product
Status:   [~] in progress
Notes:    Catalog / PIM for sellable products. Owns product.* only.
          Working list: modules/product/docs/features-list.txt
          Folder emptied 2026-08-30; rebuild skeleton (R2) then docs
          (R2b) before any feature slice. One feature per turn, F1 first.
          DB assets in Infrastructure/Persistence/ (Bootstrap, Migrations,
          Seeders, Factories). REST is format only. Other modules use
          ProductApi (DTOs). ProductUpdated → platform.outbox, same txn.

    Progress checklist
      [x] R1  Requirement analysis (Core / DB / FR / NFR / Out of scope)
      [ ] R2  Skeleton (package, provider, layers, Deptrac, empty tests)
      [ ] R2b Module docs (docs/README, folder-structure, database, api)
      [ ] R3  Schema wall test passes against real Postgres
      [ ] R4  Features F1–F15 complete
      [ ] R5  Architectural boundaries A1–A5 verified in code + tests

    Tables (owned — design: modules/product/docs/database-design.txt
            columns first; visual schema at the bottom)
      Initial (first slices)
      products           listing — id, title, slug, status, created_at
      product_variants   sellable SKU — id, product_id, sku, price, compare_at
      categories         hierarchy — id, name, parent_id, slug
      attributes         specification types — id, name, type
      product_images     gallery — id, product_id, image_url, is_thumbnail
                         (full design uses product_media)

      Also in modules/product/docs/database-design.txt (as features land)
      brands, shipping_classes, product_categories, tags, product_tags,
      collections, collection_rules, collection_products,
      product_options, product_option_values, variant_option_values,
      attribute_options, product_attribute_values, product_components,
      product_media, digital_files, product_relations, url_redirects

    Architectural boundaries (must hold)
      [ ] A1  REST API front door — format/transport only; no business rules
      [ ] A2  Schema sealed (product.*) — no cross-schema FKs or joins in
      [ ] A3  State changes emit ProductUpdated to platform.outbox, same txn
      [ ] A4  Storefront reads via optimized batch queries (<100ms target)
      [ ] A5  ProductApi contract — DTOs only

    Features — Core Identity & Pricing
      [ ] F1  Lifecycle Control: create, update, draft, publish, archive
      [ ] F2  Identifiers & Details: titles, short and long descriptions,
              brands; SKU, barcode, GTIN, UPC, EAN, ISBN, MPN
      [ ] F3  Pricing Structure: base, compare-at / sale, sale start/end
              (UTC), cost, tax status and tax class
      [ ] F4  Product Types: physical, virtual (no shipping), downloadable,
              grouped, bundles / kits, affiliate / external URLs
      [ ] F12 Catalog visibility: visible, catalog-only, search-only, hidden
      [ ] F13 Featured flag (home / merchandising)
      [ ] F14 Shipping catalog data: weight, dimensions, shipping class
              (no rate quotes)
      [ ] F15 Sold individually (one per order — catalog flag)

    Features — Variations & Media
      [ ] F5  Multi-Option Variants: SKU, barcode, price per combination,
              default variant
      [ ] F6  Attributes & Specifications: reusable specs, swatches, facet flags
      [ ] F7  Media Management: galleries, thumbnail, reorder, map to variants,
              digital downloads with limit and expiry

    Features — Organization, SEO & Operations
      [ ] F8  Categorization: nested category trees, tags, manual or
              automated collections
      [ ] F9  SEO Optimization: slugs, meta title/description, slug redirects
      [ ] F10 Relationships: related, up-sell, cross-sell, frequently bought
              together
      [ ] F11 Operations: admin list, duplicate, bulk edit, CSV import/export

    Explicitly OUT OF SCOPE for this module (do not implement here)
      [-] Stock, warehouses, reservations, backorders     → Inventory
      [-] Coupons, campaigns, B2B price lists, bundle deals → Promotions
      [-] Cart, checkout, payments, tax rates, download
          entitlement after purchase                      → Orders
      [-] Stars, reviews, Q&A                             → Customer Reviews
      [-] Shipping quotes, search engine, CMS, wishlists,
          marketplace push, subscriptions, translations,
          gift-card balances                              → later / other modules
