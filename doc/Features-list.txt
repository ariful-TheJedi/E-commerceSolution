HOW TO USE
-------------------------------------------------------------------------------
1. Developer lists modules and their features (chat, or edits this file).
2. Agent writes them here under MODULES — status starts as [ ].
3. One active module at a time. One feature / use case per turn.
4. Mark status as work moves (agent MUST flip these in the same turn
   as the work — also mirror in AGENTS.md):

       [ ]  planned
       [~]  in progress
       [x]  done
       [-]  parked / deferred

5. Each module has a Progress checklist (require → skeleton → wall →
   features). Flip those boxes when that stage finishes.
6. Each module has modules/<name>/docs/. When the module changes,
   the agent updates those docs in the same turn (brief, folder
   structure, database, api).
7. Do not start the next module until the current one's list is done
   (or the developer parks remaining items).

  Scope rules:
    Identity owns names, email, phone, credentials, sessions, roles, account
    state, addresses, verification, recovery, privacy requests, and security
    events. Password hashes and reset tokens are never exposed in DTOs/events.
    Orders owns carts and order history. Promotions owns loyalty, coupons, and
    customer pricing. Customer Reviews owns feedback. Product owns catalog
    records. Identity may expose contracts and immutable DTOs, never tables.


  IDENTITY FEATURES — NUMBERED REQUIREMENTS
  -------------------------------------------------------------------------------

    1. Registration & Account Creation
      Create a customer account with a unique normalized email, password hash,
      optional first/last name and phone. Never store plaintext passwords.
      New accounts follow the configured verification policy and default role;
      registration never creates orders, carts, or promotions data.

    2. Login & Session Token Issuance
      Verify credentials without revealing whether an email exists. Issue a
      secure opaque session token or equivalent server-managed credential with
      expiry, rotation policy, and device metadata. Raw tokens are never logged.

    3. Email Verification
      Send a single-use, expiring verification token through a mail port.
      Verification is idempotent, token values are stored hashed, and email
      changes require re-verification.

    4. Credential Recovery
      Request and complete password reset through single-use, expiring,
      hashed tokens. Responses do not disclose account existence. Successful
      reset revokes active sessions and sends a security notification.

    5. Password & Credential Changes
      Authenticated users may change a password after current-credential
      verification. Email changes require verification; credential changes
      rotate or revoke sessions. Policy checks are not controller-only rules.

    6. Session Control & Revocation
      List the current user’s sessions with safe device/time metadata, revoke
      one session, revoke all other sessions, and invalidate tokens on account
      suspension or password reset.

    7. Profile Details
      Read and update first name, last name, email, phone, and permitted
      display fields. Normalize email and phone consistently. No order totals,
      carts, reviews, loyalty, or customer pricing belong here.

    8. Address Book
      Create, update, remove, and select saved billing/shipping addresses with
      ownership checks and one optional default per purpose. Other modules ask
      through an Identity contract; historical consumers copy snapshots.

    9. Account Status & Deletion Requests
      Support active, suspended, and deletion-requested states. Suspension
      blocks authentication without deleting history. Deletion is an explicit
      authorized workflow with revocation, retention, audit, and anonymization;
      it never cascades into Orders-owned data.

    10. Roles & Permissions (RBAC)
      Define stable roles such as customer, manager, and administrator, with
      explicit permissions. Assign/revoke roles only through authorized
      administrative use cases; never trust a client-supplied role.

    11. Route Protection Integration
      Provide host middleware/policy integration for authenticated identity
      and required permissions. The Host applies middleware; Identity supplies
      authentication and authorization contracts. Modules do not own user
      lookup or role tables.

    12. Abuse Protection & Security Policy
      Rate-limit registration, login, recovery, verification, and token use;
      apply bounded login backoff/lockout and replay protection. Define secure
      cookie, CSRF, origin, and transport policy through host configuration.
      MFA or step-up authentication may be added behind a provider port.

    13. Personal Data Export & Privacy Requests
      Let authenticated users request an export of Identity-owned data and
      track its lifecycle. Support authorized deletion/anonymization requests
      with retention rules and secure delivery. Identity does not export order
      history; Orders fulfills its own data contract.

    14. Security Audit Events
      Publish immutable events for registration, login outcome, verification,
      recovery, password change, session revocation, role change, suspension,
      and deletion request. Events contain safe identifiers and times, never
      passwords, raw tokens, reset secrets, or sensitive address data.


  OUT OF SCOPE FOR IDENTITY
  -------------------------------------------------------------------------------
    [-] Orders: order history, carts, checkout, payment, fulfillment,
      download entitlements
    [-] Promotions: coupons, campaigns, loyalty points, customer pricing
    [-] Customer Reviews: stars, reviews, Q&A
    [-] Product: catalog, SKUs, inventory, product permissions
    [-] Inventory: stock, warehouses, reservations, backorders
    [-] Search, marketing subscriptions, shipping quotes, and tax rates
