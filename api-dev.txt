================================================================================
E-COMMERCE API — MODULAR MONOLITH ARCHITECTURE
================================================================================
Target     : SMB e-commerce platform
Style      : Modular Monolith (ONE deployable API, MANY internal modules)
Goal       : Ship fast now; extract modules to microservices later IF needed
Stack hint : ASP.NET Core / NestJS / similar — structure stays the same

KEY IDEA
--------
- Single codebase, single database (start), single deployment
- Features live in isolated MODULES (Catalog, Orders, Payments, …)
- Modules talk via clear interfaces / application services (not spaghetti)
- Later: any module can be moved out as its own service without rewriting business logic

LAYERS INSIDE EACH MODULE (same pattern everywhere)
---------------------------------------------------
  Api/            → Controllers / Endpoints (HTTP only)
  Application/    → Use-cases, DTOs, validators, interfaces
  Domain/         → Entities, enums, business rules
  Infrastructure/ → EF/Repository, external APIs (owned by module)


COMMUNICATION RULES (keeps monolith extendable)
-----------------------------------------------
1. Prefer: Module A → Module B via Application Interface (IOrderService)
2. Prefer: Domain Events for side effects (OrderPlaced → send email, reduce stock)
3. Avoid: Module A directly querying Module B database tables
4. Never: Circular module references
5. Shared Kernel only for truly shared primitives (Result, Money, BaseEntity, ICurrentUser)


EXTENSION PATH (when you outgrow monolith)
------------------------------------------
Phase now     : In-process method calls + domain events
Next step     : Outbox pattern + message bus (RabbitMQ/Redis)
Future        : Extract hot modules (Payments / Notifications) as separate services
              : Keep same Application contracts → adapters become HTTP/gRPC clients

RESPONSE SHAPE (standard)
-------------------------

  Error:   { "success": false, "error": { "code": "STOCK_INSUFFICIENT", "message": "..." } }

4. CROSS-CUTTING CONCERNS
================================================================================

Security
  - JWT access + refresh tokens
  - Role-based access: Customer | Staff | Manager | Owner
  - Permission checks on admin endpoints
  - Rate limit login / checkout / payment initiate

Data
  - Soft delete on products, users, orders (never hard-delete paid orders)
  - Audit fields: CreatedAt, CreatedBy, UpdatedAt, UpdatedBy
  - Idempotency key on checkout & payment initiate

Events (examples)
  - UserRegistered
  - OrderPlaced
  - OrderStatusChanged
  - PaymentCompleted / PaymentFailed
  - StockLow
  - CouponRedeemed

Config
  - Feature flags per module (enable Reviews, Loyalty, Multi-currency later)
  - Provider switches: EmailProvider, SmsProvider, PaymentProviders[]

────────────────────────────────────────────────────────────────────────────────

────────────────────────────────────────────────────────────────────────────────
PHASE 1 — MVP CORE (Weeks 2–6)  ★ MUST SHIP
────────────────────────────────────────────────────────────────────────────────
Goal: A merchant can list products and a customer can place a paid/COD order.

Modules to create
  1) Identity
  2) Catalog (+ basic Media upload)
  3) Inventory (simple stock on product/variant)
  4) Cart + Checkout (can be one module)
  5) Orders
  6) Payments (COD + 1 online gateway)
  7) Notifications (email only: order confirmation)
  8) Shipping (flat rate + zones — minimal)

Features
  [ ] Register / login / JWT / me profile
  [ ] Admin: CRUD categories & products (simple + variants)
  [ ] Public: product list, detail, search (basic)
  [ ] Stock check on add-to-cart & checkout
  [ ] Cart CRUD
  [ ] Checkout → create Order + Payment
  [ ] COD + one digital payment
  [ ] Admin: order list, status update (Pending→Confirmed→Shipped→Delivered)
  [ ] Customer: order history
  [ ] Email: order placed / status changed
  [ ] Basic store settings (currency, store name)

Domain events to wire
  OrderPlaced → reserve/reduce stock + send email
  OrderCancelled → restore stock (if rules allow)

Exit criteria
  - End-to-end happy path on Postman/Swagger
  - No oversell on concurrent simple tests
  - Admin can fulfill an order in under 1 minute


────────────────────────────────────────────────────────────────────────────────
PHASE 2 — GROWTH (Weeks 7–11)
────────────────────────────────────────────────────────────────────────────────
Goal: Retention, ops efficiency, marketing basics.

Modules / expand
  [ ] Marketing (coupons, banners)
  [ ] Reviews (with moderation)
  [ ] Shipping (weight/price rules, free-shipping threshold)
  [ ] Returns / RMA under Orders
  [ ] Notifications (SMS + email templates)
  [ ] Media (image resize, CDN path)
  [ ] Analytics (basic sales reports)
  [ ] CMS pages (Privacy, Terms, Refund, FAQ)
  [ ] Role-based staff accounts (Owner/Manager/Support)
  [ ] Bulk product CSV import/export
  [ ] Abandoned cart job (scheduled)

Features
  [ ] Coupons: %, fixed, free shipping
  [ ] Wishlist
  [ ] Product reviews approve/reject
  [ ] Low-stock admin alerts
  [ ] Refunds (full/partial)
  [ ] Invoice PDF
  [ ] Dashboard stats: sales, orders, low stock
  [ ] Audit log for staff actions

Exit criteria
  - Merchant can run a discount campaign without code changes
  - Reports export to CSV
  - Staff roles cannot access owner-only settings


────────────────────────────────────────────────────────────────────────────────
PHASE 3 — SCALE (Weeks 12–18)
────────────────────────────────────────────────────────────────────────────────
Goal: Mid-size readiness; performance & richer commerce.

Build
  [ ] Multi-warehouse inventory (optional module split)
  [ ] B2B / wholesale price lists & MOQ
  [ ] Loyalty points
  [ ] Multi-language / multi-currency (feature-flagged)
  [ ] Courier integrations (tracking webhooks)
  [ ] Advanced search (full-text / Meilisearch / ES)
  [ ] Caching layer (Redis) for catalog & sessions
  [ ] Outbox pattern for reliable events
  [ ] Rate limiting & fraud rules for COD
  [ ] PWA-related APIs if needed (push subscription)

Exit criteria
  - Catalog endpoints stay fast under higher product counts
  - Events not lost on email/SMS provider downtime (outbox)
  - B2B price correctly applied at checkout


────────────────────────────────────────────────────────────────────────────────
PHASE 4 — PLATFORM / SAAS (Later)
────────────────────────────────────────────────────────────────────────────────
Goal: Sell the product to many merchants (multi-tenant).

Build
  [ ] Tenant isolation (TenantId on all tables OR schema-per-tenant)
  [ ] Onboarding wizard APIs
  [ ] Subscription plans & billing
  [ ] Usage limits (products, staff, orders)
  [ ] Custom domain mapping
  [ ] Theme / branding settings API
  [ ] White-label options
  [ ] Platform admin (super-admin) APIs

NOTE
  Keep tenant middleware from day one as a STUB (TenantId = default)
  so Phase 4 does not require rewriting every query.

6. MODULE DEPENDENCY MAP (ALLOWED DIRECTIONS)
================================================================================

  Identity ──────────► (used by almost all; expose ICurrentUser only)

  Catalog ───────────► Inventory (stock belongs with SKU)
  Cart ──────────────► Catalog, Inventory, Marketing(coupons)
  Checkout/Orders ───► Cart, Catalog, Inventory, Shipping, Payments, Identity
  Payments ──────────► Orders (update payment status)
  Notifications ◄──── listens to events from Orders, Identity, Inventory
  Analytics ◄──────── reads Orders/Payments/Catalog (prefer read models later)
  Media ◄──────────── used by Catalog, CMS, Reviews

  SharedKernel ◄────── everyone may reference
  Infrastructure ◄──── referenced by Api host; modules use abstractions

FORBIDDEN
  Catalog must NOT reference Orders
  Payments must NOT reference Catalog directly
  Notifications must NOT be required synchronously inside checkout transaction
    (publish event → handle async/in-process after commit)


================================================================================
7. DATABASE STRATEGY
================================================================================

Phase 1–2
  - ONE database, ONE DbContext
  - Tables prefixed or grouped by module name (Catalog_Products, Orders_Orders)
  - Migrations owned by Infrastructure (or per-module migration folders)

Phase 3+
  - Logical schemas per module (catalog, orders, payments) — still one DB
  - Read models / reporting tables for Analytics

Phase 4
  - Multi-tenant: TenantId column + global query filters
  - OR database-per-large-tenant for enterprise clients

Core tables (Phase 1)
  Users, Roles, UserRoles
  Categories, Products, ProductVariants, ProductImages
  StockItems
  Carts, CartItems
  Orders, OrderItems, OrderStatusHistory
  Payments
  ShippingZones, ShippingRates
  MediaAssets
  StoreSettings

10. WHAT “EXTENDABLE MONOLITH” MEANS IN PRACTICE
================================================================================

Today
  Ecommerce.Api hosts all modules in one process

Tomorrow (example)
  Extract Ecommerce.Modules.Payments → Payments.Service
  Keep IPaymentService contract
  Replace local implementation with HTTP/gRPC client adapter
  Orders module unchanged at the application layer

You only pay the microservice cost when a module truly needs
independent scaling, team ownership, or compliance isolation.
