===============================================================================
                          C H A N G E   G U I D E
        How to add a module, change a feature, or alter the database
                          without breaking anything
===============================================================================

WHAT THIS DOCUMENT IS
    The procedures. system-design.txt says what the system's shape is;
    this one says what to actually do when you need to change it.

    Every recipe here is written as steps you can follow without thinking
    about the architecture. That is deliberate. The rules only survive if
    following them is easier than not.

WHAT THIS DOCUMENT IS NOT
    It does not name a module or a feature of the real domain. The recipes
    work for any module you later decide to build.

PLACEHOLDERS, SAME AS THE DESIGN DOCUMENT
    Module A / Module B     any two modules
    schema alpha / beta     their schemas
    widget, widget_part     any parent/child table pair

PART 1 - START HERE: WHICH KIND OF CHANGE IS THIS?
===============================================================================

    Four questions, in order. The first "yes" tells you where to go.

    ┌──────────────────────────────────────────────────────────────────┐
    │                                                                  │
    │  Q1. Is this a new capability that owns data nobody owns yet,     │
    │      and that could plausibly be turned off on its own?           │
    │          YES ──► PART 2, add a new module                         │
    │                                                                  │
    │  Q2. Does it change behaviour that clearly belongs to one         │
    │      existing module?                                             │
    │          YES ──► PART 3, add a feature to that module             │
    │                                                                  │
    │  Q3. Does it need data another module owns?                       │
    │          YES ──► PART 5 first, then PART 3                        │
    │                                                                  │
    │  Q4. Does it seem to belong to two modules at once?               │
    │          YES ──► STOP. See 1.2 below.                             │
    │                                                                  │
    │  And separately, if it touches tables at all ──► PART 4           │
    │                                                                  │
    └──────────────────────────────────────────────────────────────────┘


1.1  IS IT REALLY A NEW MODULE?

    A new module is justified when most of these are true:

        [ ] It owns data no existing module owns.
        [ ] It has its own vocabulary - words that mean something
            specific here and something different elsewhere.
        [ ] It could be switched off and the rest of the system would
            still function, minus that capability.
        [ ] It has its own rules, not just its own screens.
        [ ] Its rate of change differs from the modules around it.
        [ ] You can state its responsibility in one sentence, without
            "and".

    It is NOT a new module when:

        - It is a screen or a report over existing data.
            ► A query in the owning module, or a reporting view.
        - It is a variation of something an existing module already does.
            ► A feature in that module.
        - It has no data of its own and only calls other modules.
            ► Usually an endpoint in one of them, or a thin
              orchestration slice in the module that owns the outcome.
        - It is a technical concern with no domain meaning - caching,
          scheduling, mail delivery.
            ► Platform, not a module.

    When in doubt, put it inside an existing module as a feature. A
    feature promoted into a module later is a folder move. A module that
    should never have existed spreads coupling in every direction while
    you decide what to do with it.


1.2  IT SEEMS TO BELONG TO TWO MODULES

    This is the most important signal in the whole document, so do not
    push through it. One of four things is true:

    a) It is two features, one in each module, connected by an event.
       This is the usual answer. Split it along the "who owns the data
       being changed" line, and let the second module react.

    b) It belongs to the module that owns the *outcome*, and it needs
       information from the other. That is a contract call - Part 5.

    c) The boundary is drawn in the wrong place, and these two modules
       are one module. Merging is legitimate. See Part 9.

    d) There is a third, missing concept that owns the interaction, and
       neither existing module should. Rare, but real. That is a new
       module - Part 2.

    What is never the answer: both modules writing the same table, or one
    module reaching into the other's internals "just this once".


===============================================================================
PART 2 - ADD A NEW MODULE
===============================================================================

    Once you have confirmed it is a module (1.1), this is the sequence.
    Steps 1-4 should happen before any behaviour is written.


2.1  THE STEPS

    STEP 1 - WRITE THE ONE-LINER AND THE OWNERSHIP LIST
        In docs/decisions/, a few lines:
            - the module's name, one word
            - its responsibility, in one sentence with no "and"
            - what data it will own
            - what it explicitly does not own
            - which modules it will need to call, and why
            - which facts it will announce
        If you cannot fill in the last three, you do not understand the
        boundary yet, and writing code will not help.

    STEP 2 - CHECK THE DEPENDENCY DIRECTION
        List the modules it depends on. Then check that none of them will
        need to depend back on it. If one will, you have a cycle - resolve
        it now by converting one direction into an event, before any code
        exists. Cycles are cheap to prevent and expensive to remove.

    STEP 3 - CREATE THE SCHEMA AND THE ROLES
        Run the bootstrap SQL from system-design.txt 3.3 with the new
        name: schema, owner role, app role, grants, default privileges,
        access to `platform`. Commit it in db/bootstrap/.
        Do this before the first table, so no table is ever created in
        the wrong place.

    STEP 4 - CREATE THE FOLDERS
        Copy the module skeleton, which means two build units:
            <Name>.Contracts/    Api interfaces, Dtos, Events
            <Name>/              Api, Application, Domain,
                                 Infrastructure, and the module
                                 registration file
        And two test projects: <Name>.UnitTests and
        <Name>.IntegrationTests.
        Keep a real skeleton in the repository to copy from. A module that
        takes twenty minutes to create is a module people will create
        properly; one that takes a day is a module people will avoid by
        dumping code somewhere else.

    STEP 5 - REGISTER IT
        One line in the host's module registry. The host learns the module
        exists; the module learns nothing about the host.
        Add the module to the architecture test project's references so
        the structural rules cover it. If your discovery is by convention,
        confirm the guard test sees it.

    STEP 6 - BUILD ONE VERTICAL SLICE, THINNEST POSSIBLE
        One use case, all the way through: endpoint, handler, one entity,
        one table, one migration, one test at Level 3. Something you can
        call and see a row appear.
        Resist building the whole module before running anything. The
        first slice validates the wiring, and wiring is where the
        surprises are.

    STEP 7 - PUBLISH THE CONTRACT, ONLY WHEN SOMEONE NEEDS IT
        Do not design the public interface up front. Wait until another
        module actually needs something, then publish exactly that, with a
        batch shape from the start. An unused public interface is a
        guess, and it will be the wrong one.

    STEP 8 - PUBLISH THE FIRST EVENT, SAME RULE
        Announce facts other modules will plausibly care about. Do not
        invent subscribers. One well-named event beats five speculative
        ones.

    STEP 9 - FINISH THE VERTICAL, THEN GO WIDE
        Complete the module's own use cases before wiring it to
        everything else. A module that works alone can be integrated; a
        half-built module that is already integrated everywhere cannot be
        changed.


2.2  DEFINITION OF DONE FOR A NEW MODULE

        [ ] Decision note written, responsibility in one sentence.
        [ ] Schema, owner role, app role, grants committed.
        [ ] Two build units: contracts and internals.
        [ ] Same internal folder shape as every other module.
        [ ] Registered in the host in one line.
        [ ] Covered by the architecture test suite.
        [ ] Its migrations touch only its own schema.
        [ ] No foreign key crossing into or out of its schema.
        [ ] No reference to another module's internals.
        [ ] No other module writes its tables.
        [ ] One unit test project, one integration test project.
        [ ] At least one Level 3 test that goes endpoint to database.
        [ ] Contract, if any, is data shapes only - no entities.
        [ ] Events, if any, are past tense and immutable.
        [ ] Any external dependency is behind a port with a fake.


===============================================================================
PART 3 - ADD OR CHANGE A FEATURE IN AN EXISTING MODULE
===============================================================================

    This is the common case and it should be boring. If adding a feature
    ever requires touching four modules, something is wrong with the
    boundaries, not with your day.


3.1  THE STEPS

    STEP 1 - CONFIRM THE MODULE
        Which module owns the data this feature changes? That module owns
        the feature. Not the module whose screen shows it.

    STEP 2 - CREATE ONE FOLDER
        In that module's Application layer, one new folder named after the
        use case. Inside it: the command or query, its handler, its
        validator, its result shape. Everything that changes together
        lives together.

    STEP 3 - PUT THE RULES IN THE DOMAIN
        Any new invariant, calculation, or legal-transition rule goes in
        the Domain layer, where it can be unit tested with no database
        and no framework. The handler orchestrates; it does not decide.

    STEP 4 - ADD WHAT PERSISTENCE IT NEEDS
        New columns or tables: follow Part 4. New query: it belongs in
        this module's Infrastructure, against this module's schema only.

    STEP 5 - ADD THE ENDPOINT
        One endpoint in this module's Api folder, on the right surface
        (public / management / machine), following the conventions in
        system-design.txt Part 5. Edge validation here, business rules in
        the domain.

    STEP 6 - SIDE EFFECTS BECOME EVENTS
        If something outside this module should happen as a result -
        anything at all - publish an event and stop thinking about it. Do
        not call the other module. Do not add a flag it will poll.
        If the effect must be reliable, write the event to the outbox in
        the same transaction as the change.

    STEP 7 - TEST AT THE RIGHT LEVEL
        New domain rule ──► Level 1 unit test, cases exhaustively.
        New use case    ──► Level 3 integration test through the endpoint,
                            asserting response, database state and any
                            published event.
        Interesting branching in the handler ──► add Level 2.
        Only if the flow crosses modules and its failure is unacceptable
        ──► add or extend one Level 4 test.

    STEP 8 - UPDATE THE PUBLISHED SURFACE, IF YOU TOUCHED IT
        New response field: additive, fine. Changed or removed field:
        that is Part 8, not this part.


3.2  WHERE EACH FILE GOES

    ┌──────────────────────────────┬─────────────────────────────────────┐
    │ What you are writing         │ Where it goes                       │
    ├──────────────────────────────┼─────────────────────────────────────┤
    │ Route, request/response      │ Module/Api/                         │
    │ Use case orchestration       │ Module/Application/<UseCase>/       │
    │ Input shape validation       │ Module/Application/<UseCase>/       │
    │ Business rule, invariant     │ Module/Domain/                      │
    │ Calculation, policy          │ Module/Domain/                      │
    │ Interface for something      │ Module/Application/Ports/           │
    │ outside the module           │                                     │
    │ Implementation of that       │ Module/Infrastructure/Adapters/     │
    │ Table mapping, query, repo   │ Module/Infrastructure/Persistence/  │
    │ Migration                    │ Module/Infrastructure/Persistence/  │
    │                              │ Migrations/                         │
    │ Reaction to another module's │ Module/Application/EventHandlers/   │
    │ event                        │                                     │
    │ Event this module announces  │ Module.Contracts/Events/            │
    │ Interface others may call    │ Module.Contracts/                   │
    │ Data shape crossing modules  │ Module.Contracts/Dtos/              │
    │ Money, ids, time, result     │ SharedKernel/  (and only if truly   │
    │                              │ shared - see 12.3)                  │
    │ Bus, jobs, logging, caching  │ Platform/                           │
    └──────────────────────────────┴─────────────────────────────────────┘


3.3  DEFINITION OF DONE FOR A FEATURE

        [ ] One use-case folder, not files scattered by type.
        [ ] Rules in the domain, orchestration in the handler.
        [ ] No reference to another module's internals.
        [ ] No query touching another schema.
        [ ] Cross-module effects are events, not calls.
        [ ] Any migration is additive (Part 4).
        [ ] Tests at the level that actually proves it.
        [ ] Errors use the standard problem shape and a registered type.
        [ ] Authorisation checked inside the module, not only at the edge.
        [ ] Fine to delete: removing this feature is deleting one folder,
            one route and one migration-era column.


===============================================================================
PART 4 - CHANGE THE DATABASE
===============================================================================

    This is where a system becomes hard to change, so it gets the most
    detailed treatment. The whole part reduces to one idea: never change
    the meaning of something that already exists - add the new thing
    beside it, move over, then remove the old thing later.


4.1  CLASSIFY THE CHANGE FIRST

    ┌──────────────────────────────────────────────────────────────────┐
    │  Am I only ADDING something nobody reads yet?                     │
    │       YES ──► 4.3, additive. One migration, one deploy, done.     │
    │                                                                  │
    │  Am I changing the shape or meaning of something in use?          │
    │       YES ──► 4.5, expand-contract. Several deploys. No           │
    │               shortcuts, no exceptions.                           │
    │                                                                  │
    │  Am I removing something?                                         │
    │       YES ──► 4.6, and only after proving nothing uses it.        │
    │                                                                  │
    │  Does the change involve another module's schema?                  │
    │       YES ──► STOP. That is their migration, not yours. Two       │
    │               migrations in two modules, in a safe order.         │
    └──────────────────────────────────────────────────────────────────┘


4.2  WHAT IS SAFE AND WHAT IS NOT

    In PostgreSQL, on a table with real data and live traffic:

    ┌──────────────────────────────────────┬───────────────────────────┐
    │ Operation                            │ Safe?                     │
    ├──────────────────────────────────────┼───────────────────────────┤
    │ Add a nullable column                │ YES, instant              │
    │ Add a column with a constant default │ YES on modern Postgres,   │
    │                                      │ no table rewrite          │
    │ Add a column NOT NULL with no default│ NO - rewrites and fails   │
    │                                      │ on existing rows          │
    │ Create index CONCURRENTLY            │ YES - use always on live  │
    │                                      │ tables                    │
    │ Create index without CONCURRENTLY   │ NO - blocks writes         │
    │ Add CHECK constraint as NOT VALID,   │ YES - two steps           │
    │ then VALIDATE separately             │                           │
    │ Add CHECK constraint directly        │ NO - scans, holds a lock  │
    │ Add foreign key NOT VALID then       │ YES - within a schema     │
    │ VALIDATE                             │ only                      │
    │ Widen a varchar / drop a length cap  │ YES, metadata only        │
    │ Narrow or retype a column            │ NO - full rewrite         │
    │ Rename a column or table             │ NO - instantly breaks all │
    │                                      │ running code              │
    │ Drop a column                        │ Fast, but breaks any code │
    │ (metadata only)                      │ still selecting it        │
    │ Set NOT NULL on an existing column   │ NO directly. Add a        │
    │                                      │ validated CHECK first,    │
    │                                      │ then set NOT NULL cheaply │
    │ Add a value to a native enum type    │ Requires migration; and   │
    │                                      │ removing one is nearly    │
    │                                      │ impossible - prefer TEXT  │
    │                                      │ with a CHECK             │
    │ Backfill with one big UPDATE         │ NO - long transaction,    │
    │                                      │ bloat, lock contention.   │
    │                                      │ Batch it.                 │
    └──────────────────────────────────────┴───────────────────────────┘

    "Renaming a column is not safe" is the single most useful line here.
    A rename is atomic in the database and *not* atomic in your fleet:
    for the seconds or minutes during a rolling deploy, old code and new
    schema coexist, and old code is now broken. That is why renames are
    always expand-contract.


4.3  THE ADDITIVE RECIPE

    For new columns, new tables, new indexes, new optional things.

        1. Write the migration in the owning module's migrations folder.
        2. New columns are nullable, or have a constant default.
        3. New tables get: id, created_at, updated_at, tenant_id if the
           system is multi-tenant, and real foreign keys to other tables
           in the same schema.
        4. Add the indexes the new queries need, concurrently.
        5. Deploy the migration, then the code that uses it. In that
           order, always - so the schema is ready before anything asks
           for it.
        6. Where a new column must eventually be mandatory, get there in
           two steps later: backfill in batches, add a validated CHECK,
           then set NOT NULL.

    A pure addition is one deploy and needs no coordination. Keep as many
    of your changes as possible in this category - it is the reason
    additive-first is a law rather than a preference.


4.4  LOCKS, AND NOT TAKING THE DATABASE DOWN

    Two habits, applied to every migration on a table that has data:

    SET A LOCK TIMEOUT
        SET lock_timeout = '3s';
        SET statement_timeout = '30s';
        ALTER TABLE alpha.widget ADD COLUMN note TEXT NULL;

        Without this, a migration that cannot get its lock waits - and
        while it waits, it queues behind itself every other query wanting
        that table. A three-second failure you retry is infinitely better
        than a lock queue that stalls the application. Put these lines at
        the top of the migration runner, not in each file.

    BACKFILL IN BATCHES
        Never one UPDATE across millions of rows. Loop in batches of a
        few thousand, committing each, with a pause. Slower in wall-clock
        time, invisible to users, and interruptible.

    And one rehearsal habit: apply every migration in CI to a restored
    copy of realistic data, not just to an empty database. Almost every
    migration incident is a statement that was instant on an empty table.


4.5  EXPAND-CONTRACT: FOR EVERYTHING ELSE

    Any change to something in use - rename, retype, split a column,
    merge two, change units, change semantics - uses these six steps.
    They span multiple deploys on purpose. The system is fully working
    after every single one, and any one of them can be rolled back.

        STEP 1  EXPAND
            Add the new thing beside the old one. Nullable. Nothing reads
            it yet. Deploy.

        STEP 2  WRITE BOTH
            Change the code to write both old and new on every write.
            Reads still use the old one. Deploy.

        STEP 3  BACKFILL
            Fill the new column for existing rows, in batches, until old
            and new agree everywhere. Verify with a query that counts
            disagreements and expects zero.

        STEP 4  READ NEW
            Switch reads to the new column. Still writing both. Deploy.
            This is the step you might need to roll back, and you can,
            instantly, because the old column is still correct.

        STEP 5  STOP WRITING OLD
            Remove the old write. Deploy. Let it run long enough that you
            would have noticed a problem - days, not minutes.

        STEP 6  CONTRACT
            Drop the old column. Separate migration, separate deploy,
            after confirming nothing references it.

    WORKED EXAMPLE - changing a column that stores a decimal amount into
    the standard integer-minor-units plus currency pair.

        -- step 1: expand
        ALTER TABLE alpha.widget ADD COLUMN price_minor BIGINT NULL;
        ALTER TABLE alpha.widget ADD COLUMN currency CHAR(3) NULL;

        -- step 2: application writes price, price_minor and currency
        --         on every insert and update. reads still use price.

        -- step 3: backfill, batched
        UPDATE alpha.widget
           SET price_minor = ROUND(price * 100)::BIGINT,
               currency    = 'USD'
         WHERE price_minor IS NULL
           AND id IN (SELECT id FROM alpha.widget
                       WHERE price_minor IS NULL LIMIT 5000);
        -- repeat until zero rows affected

        -- verify
        SELECT count(*) FROM alpha.widget
         WHERE price_minor IS DISTINCT FROM ROUND(price * 100)::BIGINT;
        -- must return 0

        -- step 4: application reads price_minor + currency
        -- step 5: application stops writing price

        -- step 6: contract, days later
        ALTER TABLE alpha.widget DROP COLUMN price;
        ALTER TABLE alpha.widget ALTER COLUMN price_minor SET NOT NULL;
        ALTER TABLE alpha.widget ALTER COLUMN currency SET NOT NULL;

    It looks like a lot for one column. It is six small safe steps
    instead of one risky one, none of them requiring downtime, all of
    them reversible. And after you have done it twice it is muscle
    memory.


4.6  REMOVING SOMETHING

    Removal is the step people skip, and skipping it leaves the schema
    full of columns nobody dares touch because nobody knows if they are
    used. So removal has a procedure too:

        1. Prove nothing reads it. Grep the codebase; check the query
           logs for a period; if it is exposed through the API, check
           access logs for the field.
        2. Announce it if it is published - see Part 8 for the API and
           Part 6 for events.
        3. Stop writing it. Deploy. Wait a stated period.
        4. Drop it, in its own migration, with nothing else in that
           migration.

    Never drop a table and a column and rename something in the same
    migration. When a migration goes wrong you want to know exactly which
    statement it was.


4.7  THE FIVE COUPLINGS TO WATCH FOR, AND THEIR FIXES

    Whenever a database change feels hard, it is one of these:

    ┌──────────────────────────┬───────────────────────────────────────┐
    │ Symptom                  │ Fix                                   │
    ├──────────────────────────┼───────────────────────────────────────┤
    │ "I cannot change this    │ Two modules write the table. Split    │
    │ table without checking   │ the table by owner, or convert one    │
    │ another module"          │ writer into a contract call/event.    │
    ├──────────────────────────┼───────────────────────────────────────┤
    │ "Changing this column    │ Internals are leaking through the     │
    │ breaks another module's  │ contract. Contracts expose data       │
    │ code"                    │ shapes, never table shapes. Map at    │
    │                          │ the boundary.                         │
    ├──────────────────────────┼───────────────────────────────────────┤
    │ "These two migrations    │ A foreign key crosses schemas.        │
    │ must deploy in order"    │ Remove it; store the id only.         │
    ├──────────────────────────┼───────────────────────────────────────┤
    │ "This deploy needs       │ A rename or retype in place. Use      │
    │ downtime"                │ expand-contract.                      │
    ├──────────────────────────┼───────────────────────────────────────┤
    │ "Old records changed     │ A historical fact was stored as a     │
    │ when someone edited a    │ live reference. It should have been   │
    │ record elsewhere"        │ copied in - a snapshot.               │
    └──────────────────────────┴───────────────────────────────────────┘


4.8  DEFINITION OF DONE FOR A DATABASE CHANGE

        [ ] Migration lives in the owning module, touches one schema.
        [ ] Classified: additive, expand-contract, or removal.
        [ ] Nothing renamed in place.
        [ ] No foreign key crossing a schema boundary.
        [ ] Indexes created concurrently; new reference columns indexed.
        [ ] lock_timeout set; any backfill is batched.
        [ ] Applied in CI to a restored realistic dataset, not just an
            empty database.
        [ ] Rollback plan stated, even if it is "the previous deploy
            still works because the change is additive".
        [ ] Deploy order recorded when it matters: schema first, then
            code.


===============================================================================
PART 5 - I NEED DATA THAT ANOTHER MODULE OWNS
===============================================================================

    The most frequent architectural decision you will make, and the one
    where a wrong choice does the most damage. Answer one question:


5.1  THE DECISION

    ┌──────────────────────────────────────────────────────────────────┐
    │  Do I need it as it is RIGHT NOW, or as it WAS at some moment?    │
    │                                                                  │
    │  AS IT WAS ──► copy the values into my own table at the time of   │
    │                the event, and never update the copy. Done.        │
    │                (Zone 3 - a snapshot)                              │
    │                                                                  │
    │  RIGHT NOW ──► how often, and how much?                           │
    │                                                                  │
    │     A few records, occasionally                                   │
    │        ──► batch contract call, join in memory. Start here.       │
    │                                                                  │
    │     A list I need to filter or sort by their fields              │
    │        ──► read model in my schema, fed by their events.          │
    │                                                                  │
    │     A ranking or search over their data                           │
    │        ──► extend their contract; let them answer it with their   │
    │            own indexes.                                          │
    │                                                                  │
    │     An admin dashboard or export mixing everything                │
    │        ──► a view in the reporting schema.                        │
    └──────────────────────────────────────────────────────────────────┘

    Default to the batch contract call. Measure before you build a read
    model. Two queries and an in-memory stitch is a few milliseconds, and
    a read model is a permanent piece of infrastructure with eventual
    consistency, a rebuild path, and a class of bug where it silently
    drifts.


5.2  RECIPE - ADD A CONTRACT METHOD TO SOMEONE ELSE'S MODULE

        1. Define what you need as a question in their vocabulary, not
           yours. "Are these ids valid and active" not "give me rows".
        2. Add the method to their Contracts build unit, taking a
           collection and returning a collection. Batch from the start.
        3. Return a data shape owned by their contract. Never an entity,
           never a persistence type.
        4. Implement it in their module, using their indexes.
        5. Add a contract test that calls the interface directly, not
           through HTTP - that is the path that survives extraction.
        6. In your module, call it once per request with all the ids.
           Never inside a loop.
        7. Handle the "not found" case as a normal outcome. Ids can stop
           resolving, and that must degrade, not throw.


5.3  RECIPE - BUILD A READ MODEL

    Only after 5.1 says you need one.

        1. Design the table backwards from the screen. One row per row
           displayed, every column you filter or sort by, nothing else.
        2. Create it in YOUR schema. It is your table; you own it.
        3. Subscribe to the owner's events and maintain it. Handlers must
           be idempotent - the same event twice must leave the same
           state.
        4. Store `synced_at`, and expose staleness somewhere you can see
           it.
        5. Build the rebuild path in the same pull request as the table.
           A projection you cannot rebuild from scratch is a projection
           you cannot fix. Test the rebuild.
        6. Accept, in writing, that this data is eventually consistent,
           and never use it to make a write-path decision. Decisions read
           from the owner.

    THE EVENT YOU NEED DOES NOT EXIST YET
        Ask the owner to publish it - Part 6. Do not poll their tables,
        and do not add a synchronous call in a loop as a substitute.


5.4  WHAT NOT TO DO, EVER

        - Query their schema directly, even read-only, even "temporarily".
        - Add a foreign key into their table.
        - Import their entity, repository or DbContext.
        - Call their HTTP endpoint from inside your module.
        - Write to their table because "it is only a status flag".

    Each of these takes about ten minutes to write and about a quarter to
    undo.


===============================================================================
PART 6 - ADD OR CHANGE AN EVENT
===============================================================================

6.1  ADDING A PUBLISHED EVENT

        1. Name it as a fact that already happened, past tense, in the
           publisher's vocabulary.
        2. Define it in the publisher's Contracts/Events folder.
           Immutable. Only simple types, shared-kernel types, and its own
           nested shapes.
        3. Include: the identifier of the thing, when it happened, and
           the few values a subscriber genuinely needs. Not the whole
           object graph - subscribers that need more should ask through
           the contract.
        4. Include a stable event id, so subscribers can deduplicate.
        5. Publish it inside the transaction via the outbox if anything
           important depends on it arriving; publish directly only for
           things you can afford to lose.
        6. Add a serialisation test with a stored sample payload.
        7. Do not create subscribers speculatively. The event can exist
           with zero subscribers - that is fine and normal.


6.2  SUBSCRIBING TO ONE

        1. Handler goes in your module's Application/EventHandlers.
        2. It must be idempotent. Either check whether you have already
           processed this event id, or make the operation naturally
           repeatable. Assume redelivery, because retries exist.
        3. It runs in its own transaction, and it writes only your
           schema.
        4. If it fails, it must not affect the publisher. Retry with
           backoff, then park the message somewhere visible, and alert.
           Silent event loss is the worst failure mode in this
           architecture because nothing breaks until much later.
        5. Never assume ordering between different event types. If order
           matters, the handler must tolerate arriving early - usually by
           ignoring what it cannot yet act on, and acting when the other
           event arrives.
        6. Test: the handler works; the handler run twice equals the
           handler run once.


6.3  CHANGING AN EVENT

    An event is a published contract, so Law 5 applies.

        ADDING A FIELD          Additive. Optional. Existing subscribers
                                keep working, unaware. Allowed freely.

        REMOVING OR RENAMING    Not allowed in place. Publish a new
        A FIELD                 version of the event alongside the old
                                one; migrate subscribers; then stop
                                publishing the old one after a stated
                                period.

        CHANGING THE MEANING    The most dangerous change, because
        OF A FIELD              nothing breaks - subscribers keep
                                reading it and are now silently wrong.
                                Treat it as a new field with a new name,
                                never a redefinition.

        RENAMING THE EVENT      New event published in parallel,
                                subscribers moved, old one retired.

        DELETING THE EVENT      Only after every subscriber is gone and
                                you have verified it in the logs.


===============================================================================
PART 7 - ADD OR SWAP AN EXTERNAL PROVIDER
===============================================================================

    Anything outside the process: payment, mail, SMS, storage, search,
    shipping rates, tax calculation, any third-party API.

    THE RECIPE

        1. Define the port in terms of what your module needs, in your
           own vocabulary. `SendNotification(recipient, template, data)`
           - never `CallProviderXApi(payload)`. The moment the vendor's
           concepts appear in the interface, you have adopted the vendor
           permanently.
        2. Put the port in Application/Ports of the module that needs it.
           It belongs to the consumer, not to a shared folder - two
           modules needing "storage" may genuinely need different
           interfaces.
        3. Implement the adapter in Infrastructure/Adapters. Every piece
           of vendor detail - SDK types, field names, error codes, retry
           semantics - stops here and never travels inward.
        4. Every outbound call gets a timeout, a retry policy with
           backoff and jitter for transient failures only, and a circuit
           breaker if the provider being down should degrade rather than
           fail.
        5. Never let a provider's failure shape become a domain error.
           Translate at the adapter into your own error vocabulary.
        6. Write a fake implementation of the port in TestSupport. All
           Level 1-3 tests use it.
        7. Write a small set of real tests against the provider's
           sandbox, run on a schedule rather than every commit.
        8. Secrets in configuration, never in code, never in the
           repository, different per environment.

    SWAPPING A PROVIDER LATER
        Write a second adapter. Switch the registration in the
        composition root, behind a flag if you want to move gradually.
        No module code changes. If a module changes when you swap a
        provider, the port was leaking vendor concepts and step 1 was
        skipped.

    INBOUND CALLBACKS FROM A PROVIDER
        Verify the signature. Respond immediately with success. Do the
        work asynchronously. Make it idempotent - providers retry, and
        they deliver out of order. Record the raw payload before
        processing, so you can replay when your handler was wrong.


===============================================================================
PART 8 - CHANGE THE PUBLIC API
===============================================================================

8.1  ADDITIVE - JUST DO IT

        - A new endpoint.
        - A new optional field in a request.
        - A new field in a response.
        - A new optional query parameter, with the old default preserved.
        - A new enum value, given that clients are documented as
          tolerating unknown values.

    No version bump, no announcement. This is why additive-first matters:
    the overwhelming majority of changes cost nothing.


8.2  BREAKING - HAS A PROCESS

    Breaking means: removing or renaming a field, changing a type,
    making an optional field required, tightening validation, changing a
    status code, changing an error `type` URI, changing pagination, or
    changing the meaning of an existing field.

        1. Add the new form beside the old one. Both work.
        2. Mark the old form deprecated: `Deprecation` and `Sunset`
           response headers, a note in the documentation, and a log entry
           on every use.
        3. Watch the logs to find out who is still calling it. Contact
           them if you can.
        4. Keep it alive for the stated window. The window is a promise,
           not an aspiration.
        5. Remove it when the logs are quiet, or when the window expires
           and you have told the remaining callers.

    A new major version (`/v2`) is for when the changes are so extensive
    that steps 1-5 per field would be absurd. That should be rare. Two
    live versions is a real maintenance cost; three is a problem.


8.3  ADDING A NEW SURFACE OR CLIENT

    A new kind of caller - a mobile app, a partner integration, an
    internal tool - is a new surface (system-design.txt 5.2) with its own
    prefix, authentication, rate limits and version, contributed by the
    same modules. It is not a new module, and it is not a reason to change
    an existing surface.


===============================================================================
PART 9 - SPLIT, MERGE, RENAME OR DELETE A MODULE
===============================================================================

    Boundaries drawn early are sometimes wrong. Redrawing them is normal
    maintenance, not an admission of failure - but do it deliberately.

    SPLIT A MODULE THAT GREW TOO BIG
        Signals: two groups of use cases that never touch each other's
        tables; two vocabularies; two rates of change; a name that needs
        "and" in it.
            1. Draw the line through the tables first, not the code. If
               the tables do not separate cleanly, neither will the code.
            2. Create the new module and schema (Part 2).
            3. Move the tables: create in the new schema, dual-write,
               backfill, switch reads, stop writing old, drop. This is
               expand-contract at table scale.
            4. Move the code folders.
            5. Any link between the two halves that used to be a foreign
               key becomes an id reference plus a contract call (Part 5).
            6. Publish contracts and events for what they now need from
               each other.

    MERGE TWO MODULES THAT SHOULD BE ONE
        Signals: almost every feature touches both; the contract between
        them keeps growing; they constantly need each other's data in
        the same transaction.
            1. Pick which schema survives.
            2. Move tables into it, using the same expand-contract steps.
            3. Delete the contract between them - internal calls are now
               ordinary calls.
            4. Delete the events that only existed to cross the boundary.
            5. Keep the events other modules subscribe to.

    RENAME A MODULE
        Cheap in code, expensive in the database. Rename the folders and
        build units freely. Renaming the schema is a table migration, so
        it is usually not worth it - a schema whose name is slightly
        stale is a small, well-documented cost.

    DELETE A MODULE
        1. Remove its routes; confirm no traffic for a period.
        2. Remove its registration line from the host.
        3. Remove subscriptions to its events; then its events.
        4. Remove other modules' references to its contract.
        5. Archive its data before dropping the schema.
        6. Delete the folder and the schema, in separate commits.

        If step 4 turns out to be hard, that is your feedback on how well
        the boundaries were kept. In a healthy system, deleting a module
        is a small pull request.


===============================================================================
PART 10 - EXTRACT A MODULE INTO A SERVICE
===============================================================================

    Only for a reason from system-design.txt 7.2. Then:

        1. AUDIT against the six extraction-ready properties (2.4 of the
           design document). Fix any that fail while everything is still
           in one process - it is far cheaper there.
        2. FIND THE HIDDEN COUPLING. Search for: any query naming its
           schema from outside, any transaction spanning its schema and
           another, any shared-kernel type it exposes in its contract,
           any synchronous call chain passing through it.
        3. MOVE THE DATA. Its schema becomes its own database. Reporting
           views that referenced it break - intentionally - and become a
           data pipeline.
        4. REPLACE THE CONTRACT IMPLEMENTATION with a network client
           behind the same interface. Callers do not change.
        5. ADD WHAT THE NETWORK DEMANDS: timeouts, retries, circuit
           breaker, a fallback for when it is unavailable, and tracing
           across the hop.
        6. MOVE ITS EVENTS to a broker, keeping the outbox on the
           publishing side and idempotency on the consuming side. Both
           already exist, which is the point of building them early.
        7. HANDLE THE NAMED TRANSACTION EXCEPTIONS from design 3.7. Each
           already has a documented replacement - typically a reservation
           with a timeout, or a saga with compensation.
        8. DEPLOY IT SEPARATELY, and add the operational baseline:
           its own health check, dashboard, alerts and on-call notes.

    Extract one. Live with it for a while. Only then consider a second.


===============================================================================
PART 11 - CHECKLISTS
===============================================================================

11.1  EVERY PULL REQUEST

        [ ] Does this touch only one module? If not, why not?
        [ ] Any import from another module that is not its contract?
        [ ] Any SQL naming another module's schema?
        [ ] Any new foreign key crossing a schema?
        [ ] Is the migration additive, or a full expand-contract plan?
        [ ] Any rename in place?
        [ ] New cross-module effect: is it an event rather than a call?
        [ ] New event handler: is it idempotent, and is that tested?
        [ ] New contract method: does it take and return collections?
        [ ] New external call: behind a port, with a timeout and a fake?
        [ ] New response field: additive? Removed field: deprecated
            properly?
        [ ] Errors use the standard problem shape and a registered type?
        [ ] Money as minor units plus currency? Timestamps as UTC?
        [ ] Tests at the level that actually proves the change?
        [ ] Architecture suite green?
        [ ] Could this feature be deleted by removing one folder?

11.2  THE FIVE-MINUTE REVIEW

    When you have no time for the full list, these five catch most of the
    damage:

        1. An import or a query that crosses a module boundary.
        2. A migration that renames, retypes, or sets NOT NULL directly.
        3. A synchronous call where an event belongs.
        4. A contract exposing an entity or a persistence type.
        5. A new table with no clear single owner.

11.3  MONTHLY, TAKES AN HOUR

        [ ] Has the shared kernel grown? What was added, and why?
        [ ] Are contracts growing faster than modules? That means
            boundaries are in the wrong place.
        [ ] Any module now depended on by everything? It is either a
            genuine foundation or a god module.
        [ ] Any cross-boundary orphan references, per the integrity job?
        [ ] Any deprecated field or event past its sunset date?
        [ ] Any read model that has drifted from its source?
        [ ] Any test in the suite that people routinely re-run to make it
            pass? Fix or delete it - a flaky test costs more trust than
            it provides.
        [ ] Any indexes never used? Any missing on cross-schema
            reference columns?


===============================================================================
PART 12 - ANTI-PATTERNS AND RED FLAGS
===============================================================================

12.1  IN THE DATABASE

    A table two modules write.
        The most damaging one, because nothing in the code shows it.
    A foreign key across schemas.
        Welds deployment and maintenance windows together.
    A cross-schema join in a module.
        Whatever it powers will need rewriting at extraction.
    A "common" or "core" or "misc" schema that keeps growing.
        Unowned data. Every module ends up depending on it. If it is
        machinery, it belongs in platform; if it has meaning, it belongs
        to a module.
    A live reference where a snapshot belonged.
        History silently rewrites itself. Found months later, usually by
        a customer.
    A nullable column that everything checks for null.
        A missing table or a missing state, wearing a disguise.

12.2  IN THE CODE

    A contract that exposes entities.
        Every internal change becomes someone else's breaking change.
    A synchronous call chain three modules deep.
        One slow module makes three endpoints slow, and a cycle is one
        refactor away.
    Two modules calling each other.
        A cycle. One direction must become an event.
    An event handler that must run before the publisher's response is
    returned.
        That is not an event, that is a call. Be honest about which one
        you need.
    A module reading its own configuration about another module.
        Coupling through configuration is still coupling.
    A "manager", "helper" or "utils" file that grows steadily.
        It is a domain concept nobody has named yet.

12.3  IN THE SHARED KERNEL

    Anything with a business rule in it.
        Business rules belong to one module. A rule in the shared kernel
        is a rule every module now shares whether it wants to or not.
    Anything that changes often.
        The shared kernel is stable vocabulary. If it changes monthly, it
        is not vocabulary.
    Anything only two modules use.
        Two modules is not "shared". Duplicate it, or put it in one and
        publish it through a contract. Duplication between modules is
        usually cheaper than coupling.

12.4  IN PROCESS

    "We will add the tests after launch."
        The architecture tests are the architecture. Without them, in six
        months this document describes a system that no longer exists.
    "Just this once, I will query their table."
        There is no once. It gets copied by the next person, who assumes
        it was reviewed and approved.
    "We will separate the schemas later."
        Later is the most expensive refactor in this whole document.
    "We do not need the boundary, it is a small project."
        The boundary costs an afternoon now. Not having it costs a
        quarter later. That trade never improves with time.
