===============================================================================
                      L A R A V E L   G U A R D R A I L S
        How the architecture is achieved in Laravel, and what it costs
===============================================================================

WHY THIS DOCUMENT EXISTS
    `Dev/system-design.txt` is stack-independent and stays that way. This
    document is the Laravel-specific half: for each architectural rule, how
    it is achieved in Laravel, what enforces it, and which framework
    features are restricted as a result.

    It exists because Laravel will not enforce this architecture for you.
    In a compiled stack, reaching into another module's internals fails to
    build. In Laravel, it works, it looks idiomatic, and nothing complains.
    Everything below is a substitute for that missing compiler.

    Decision and reasoning: `docs/decisions/0001-stack.md`.

THE ONE THING TO UNDERSTAND
    Laravel's ergonomics pull toward a shared model layer over a shared
    schema. That is what makes it fast, and it is the opposite of what we
    decided. So this document restricts specific Laravel features. When a
    tutorial shows something this document forbids, the tutorial is not
    wrong - it is solving a different problem.

PLACEHOLDERS, AS IN THE OTHER DOCUMENTS
    modules alpha / beta, table widget. No real module names here.

PART 2 - PACKAGE PER MODULE
===============================================================================

2.1  WHY NOT JUST FOLDERS

    A folder under `app/` gives you nothing. Everything is one autoload
    root, so any class can `use` any other class, and a module has no
    declared dependencies to check against.

    A Composer package gives you a `composer.json` that *states* what the
    module depends on. That statement is the thing Deptrac and code review
    check against, and it is the closest Laravel gets to a project
    reference. Folder-based module packages are the weak version - skip
    them.

2.2  TWO PACKAGES PER MODULE

    modules/alpha-contracts/     the public surface. Interfaces, DTOs,
                                 events. Depends on `shared` only.
    modules/alpha/               everything else. May depend on
                                 `shared`, `platform`, and other
                                 modules' `-contracts` packages. Never
                                 on another module's implementation
                                 package.

2.3  WIRING THEM UP

    Root composer.json:

        "repositories": [
            { "type": "path", "url": "modules/*" },
            { "type": "path", "url": "packages/*" }
        ],
        "require": {
            "app/shared":          "*",
            "app/platform":        "*",
            "app/alpha":           "*",
            "app/alpha-contracts": "*"
        }

    Each package declares its own dependencies and its own PSR-4 autoload
    root. A module's composer.json is a readable statement of what it
    actually couples to - keep it short, and treat every addition to it as
    a decision.

2.4  THE SERVICE PROVIDER IS THE MODULE'S REGISTRATION

    One provider per module, and it is the only place the module announces
    itself. It binds ports to adapters, loads its routes, loads its
    migrations, and registers its event listeners.

        final class AlphaServiceProvider extends ServiceProvider
        {
            public function register(): void
            {
                $this->app->bind(WidgetRepository::class,
                                 EloquentWidgetRepository::class);
                $this->app->bind(AlphaApi::class, AlphaApiFacadeless::class);
            }

            public function boot(): void
            {
                $this->loadRoutesFrom(__DIR__.'/Api/Routes/api.php');
                $this->loadMigrationsFrom(__DIR__.'/Infrastructure/Persistence/Migrations');
            }
        }

    The application knows a module exists through one provider entry. That
    is the composition root from the design document. Nothing else in the
    application refers to the module by name.

PART 4 - ELOQUENT CONTAINMENT
===============================================================================

    This is the most important part of this document, because Eloquent is
    both the best thing about Laravel and the single largest threat to this
    architecture.

4.1  THE FOUR RULES

    RULE 1 - MODELS NEVER LEAVE INFRASTRUCTURE
        An Eloquent model may be referenced only inside
        `Infrastructure/Persistence/`. It never appears in a controller
        signature, a handler, a domain class, a DTO, an event, or an API
        resource. Repositories accept and return domain objects.

    RULE 2 - NO RELATION CROSSES A MODULE
        Within a module: relations are fine, encouraged even, because both
        tables share an owner and a schema.
        Across modules: forbidden. `$widget->subscription` where
        subscription belongs to another module is the cross-schema join
        rule 7 forbids, and it will silently work until the day the module
        is extracted. Cross-module reads go through the contract.

    RULE 3 - NO MODEL IN A ROUTE OR CONTROLLER
        Route model binding is convenient and it puts a persistence type
        into your HTTP layer. Bind the id, load through the repository.

    RULE 4 - NO QUERY OUTSIDE THE OWNING MODULE
        No `DB::table('alpha.widget')` from anywhere but module alpha. The
        per-schema database role makes this fail at runtime too, which is
        the point of configuring the roles.

4.2  WHAT THIS COSTS, HONESTLY

    You lose some of Laravel's speed. A repository that maps a model to a
    domain object is boilerplate that a pure-Eloquent application does not
    have. Roughly, for each entity, one model, one repository, one domain
    class, and a mapping between them.

    Where to be pragmatic: for a use case that genuinely just reads rows
    and returns them - a list endpoint, a lookup - a query in the
    repository returning a readonly DTO straight to the API resource is
    fine. You do not need a domain object to carry data that has no rules
    attached to it. This mirrors design section 2.5: layers are a place for
    complexity to go, not a quota to fill.

    Where not to be pragmatic: anything with a rule, a state transition, or
    money. That goes through the domain, always.

4.3  THE SHAPE OF A REPOSITORY

        // Application/Ports/WidgetRepository.php   (the port)
        interface WidgetRepository
        {
            public function find(WidgetId $id): ?Widget;
            public function save(Widget $widget): void;
        }

        // Infrastructure/Persistence/Repositories/...  (the adapter)
        final class EloquentWidgetRepository implements WidgetRepository
        {
            public function find(WidgetId $id): ?Widget
            {
                $row = WidgetModel::query()->find($id->value);
                return $row ? $this->toDomain($row) : null;
            }
            // toDomain() and toModel() are the only places the two
            // representations meet.
        }

    The domain class knows nothing about the table. That is what makes the
    domain unit-testable with no database, and what lets the table change
    without touching the rules.

PART 5 - DATABASE CONNECTIONS AND MIGRATIONS
===============================================================================

5.1  ONE CONNECTION PER MODULE

    config/database.php, one entry per module, each with the module's own
    credentials and its own search path:

        'alpha' => [
            'driver'      => 'pgsql',
            'host'        => env('DB_HOST'),
            'database'    => env('DB_DATABASE'),
            'username'    => env('ALPHA_DB_USERNAME'),   // alpha_app
            'password'    => env('ALPHA_DB_PASSWORD'),
            'search_path' => 'alpha,platform',
            'charset'     => 'utf8',
        ],

    Each module's models declare their connection:

        protected $connection = 'alpha';

    Two consequences worth noticing. Unqualified table names now resolve
    to the module's own schema, so ordinary code cannot accidentally reach
    another module's tables. And because `alpha_app` has no permission on
    other schemas, an attempt to do so fails at runtime with a permission
    error rather than silently succeeding. That runtime failure is your
    substitute for a compiler.

5.2  MIGRATIONS

    Each module's provider registers its own migration directory, so
    migrations are discovered without a central list:

        $this->loadMigrationsFrom(
            __DIR__.'/Infrastructure/Persistence/Migrations'
        );

    Run per module against its own connection:

        php artisan migrate --database=alpha \
          --path=modules/alpha/src/Infrastructure/Persistence/Migrations

    Because each connection has its own `search_path`, each module gets its
    own `migrations` history table inside its own schema. Independent
    history is what lets modules migrate independently.

    THE RULES, RESTATED FOR LARAVEL
        - A migration file names exactly one schema.
        - Use the owner role for migrations, not the app role. The app
          role deliberately cannot run DDL.
        - Never `->foreign()` to a table in another module's schema.
        - Never `renameColumn`. Expand-contract, per change-guide 4.5.
        - Set the lock timeout at the top of the migration:
              DB::statement("SET lock_timeout = '3s'");
        - `->uuid('id')->primary()` with the database default `uuidv7()`,
          or generate an ordered UUID in PHP. Verify what your Laravel and
          PostgreSQL versions provide rather than assuming.
        - Cross-module reference columns: plain `uuid`, no foreign key,
          always indexed, always with the comment explaining why there is
          no constraint.

PART 6 - EVENTS, QUEUES AND THE OUTBOX
===============================================================================

6.1  TWO KINDS, KEPT APART

    Inside a module, ordinary Laravel events and listeners are fine. They
    may carry the module's own types.

    Across modules, the event class lives in the publishing module's
    `-contracts` package, contains only plain types and shared-kernel
    types, and is immutable (readonly). A subscriber depends on the
    contracts package, never on the publisher's implementation package.

6.2  WHY LARAVEL'S QUEUE IS NOT AN OUTBOX

    Laravel can dispatch a job after the transaction commits, which
    correctly avoids acting on data that then rolls back. But if the
    process dies between the commit and the dispatch, the job is simply
    gone. Nothing retries it, because nothing recorded that it should
    exist.

    For anything involving money, stock, or an externally visible promise,
    that is not good enough. So:

        1. In the same transaction as the business change, insert a row
           into `platform.outbox`: event id, type, payload, occurred_at,
           processed_at NULL.
        2. Commit. The event now cannot be lost - it is a row.
        3. A worker reads unprocessed rows, dispatches them to the bus,
           and marks them processed.

    Use the plain dispatch for things you can afford to lose - a cache
    warm, an internal metric. Use the outbox for everything else.

6.3  IDEMPOTENT HANDLERS

    Because delivery retries, every cross-module listener must be safe to
    run twice. Record processed event ids in `platform.processed_events`
    and return early on a repeat, or make the write naturally repeatable.
    This is a promise, so it gets a test: handler run twice equals handler
    run once.

    Listeners run in their own transaction and write only their own
    module's schema. A failing listener retries with backoff, then parks
    the message somewhere visible and alerts. Silent event loss is the
    worst failure mode in this architecture, because nothing appears
    broken until much later.

PART 7 - PORTS AND ADAPTERS IN LARAVEL
===============================================================================

7.1  THE FACADE AND HELPER BAN

    Laravel's facades and global helpers are the mechanism by which
    dependencies become invisible. `auth()`, `request()`, `config()`,
    `now()`, `Cache::`, `DB::`, `Http::`, `Mail::` - each one is a
    dependency that does not appear in a constructor, cannot be
    substituted in a test without framework help, and hides coupling from
    every static analysis tool.

        Domain layer:       none of them. Ever. Plain PHP only.
        Application layer:  none of them. Inject what you need.
        Infrastructure:     fine - this is where framework detail belongs.
        Api layer:          fine for framework-shaped concerns.

    Time in particular: the domain receives a Clock port, never `now()`.
    Same for generated ids and randomness. Tests that depend on the actual
    wall clock fail at midnight and cost more trust than the feature was
    worth.

7.2  EXTERNAL PROVIDERS

    Port interface in `Application/Ports`, named in your vocabulary, not
    the vendor's. Adapter in `Infrastructure/Adapters`, holding every
    piece of vendor detail - SDK types, field names, error codes.

    Every outbound call gets a timeout, a retry policy with backoff for
    transient failures only, and a circuit breaker where the provider
    being down should degrade rather than fail. Translate the provider's
    errors into your own error vocabulary at the adapter. A fake
    implementation lives in the test support package and is what all unit
    and integration tests use.

    Full recipe in change-guide Part 7.

PART 8 - THE API LAYER
===============================================================================

    Laravel gives you most of design Part 5 directly. The mapping:

    ┌──────────────────────────┬──────────────────────────────────────────┐
    │ Requirement              │ Laravel mechanism                        │
    ├──────────────────────────┼──────────────────────────────────────────┤
    │ Edge validation → 422    │ FormRequest per endpoint, in the         │
    │                          │ module's Api/Requests                    │
    │ Response shaping         │ API Resources, in Api/Resources          │
    │ Cursor pagination        │ `cursorPaginate()` - use this, not       │
    │                          │ `paginate()`, for anything that grows    │
    │ Problem details errors   │ One handler in bootstrap/app.php that    │
    │                          │ renders application/problem+json for     │
    │                          │ every failure. No module formats its own │
    │ Idempotency-Key          │ Middleware in app/Http/Middleware,       │
    │                          │ storing keys in the platform schema      │
    │ Versioning               │ Route prefix `/api/v1`, per surface       │
    │ Token auth               │ Sanctum tokens for the React client      │
    │ Rate limiting            │ Named rate limiters, per surface         │
    │ Correlation id           │ Middleware: accept or generate, put in   │
    │                          │ the log context, return in errors        │
    │ OpenAPI                  │ Generated from the code, committed, and  │
    │                          │ diffed in CI                             │
    └──────────────────────────┴──────────────────────────────────────────┘

    THE TWO PLACES TO BE CAREFUL

    Validation is two layers, not one. FormRequest handles shape, types
    and required fields. Business rules - is this transition legal, is
    this allowed in this state - live in the domain, because the module is
    also reachable through its contract where no FormRequest runs. A rule
    enforced only in a FormRequest is a rule that does not exist.

    Authorisation is also two layers. Middleware and policies at the edge
    decide whether the caller may reach the endpoint. The module decides
    whether this specific record is theirs and this transition is
    permitted. The second cannot be skipped, for the same reason.

PART 9 - THE ENFORCEMENT TOOLING
===============================================================================

9.1  DEPTRAC - THE WALL

    Deptrac is what replaces the compiler. It reads your code, assigns
    classes to layers, and fails when a dependency crosses a line you did
    not allow. It must run in CI and it must fail the build.

    Sketch of the configuration - one layer per module per architectural
    layer, then rules that mirror design Part 6.3:

        deptrac:
          paths: [ ./modules, ./packages, ./app ]
          layers:
            - name: AlphaDomain
              collectors:
                - type: directory
                  value: modules/alpha/src/Domain/.*
            - name: AlphaApplication
              collectors:
                - type: directory
                  value: modules/alpha/src/Application/.*
            - name: AlphaInfrastructure
              collectors:
                - type: directory
                  value: modules/alpha/src/Infrastructure/.*
            - name: AlphaContracts
              collectors:
                - type: directory
                  value: modules/alpha-contracts/src/.*
            # ... and the same four for every other module
            - name: Shared
            - name: Platform
            - name: Host

          ruleset:
            AlphaDomain:        [ Shared ]
            AlphaApplication:   [ AlphaDomain, Shared, BetaContracts ]
            AlphaInfrastructure:[ AlphaDomain, AlphaApplication, Shared,
                                  Platform ]
            AlphaApi:           [ AlphaApplication, Shared ]
            AlphaContracts:     [ Shared ]
            Shared:             [ ]
            Platform:           [ Shared ]

    Read what that ruleset says. Domain may touch only the shared kernel.
    Application may call another module's *contracts* and nothing else of
    it. Api cannot reach infrastructure. Shared depends on nothing. Every
    one of those lines is a rule from the design document, now automated.

    When you add a module, you add its four layers and its ruleset entry.
    That is the moment to think about what it may depend on - which is
    exactly when you should be thinking about it.

9.2  PHPSTAN - THE TYPES

    Larastan at a high level, from day one. Retrofitting types into a
    grown PHP codebase is miserable, and the value for someone still
    learning is high: it catches your mistakes as you type rather than in
    production.

    Raise the level over time if a high level is too painful at first, but
    never lower it, and never add blanket ignores. A baseline file for
    pre-existing issues is acceptable; a growing baseline is not.

9.3  PEST ARCHITECTURE TESTS

    Pest can assert structural rules directly, and it complements Deptrac
    by checking things Deptrac does not - naming, immutability, and what
    types appear in signatures. Encode at least:

        - Domain classes do not use anything from Illuminate.
        - No class outside Infrastructure/Persistence references an
          Eloquent model.
        - Contracts classes are readonly, and contain no model, no
          repository, no query.
        - Published event names are past tense.
        - A guard test that the rules matched at least one module, so a
          rename can never make the suite silently pass by checking
          nothing.

    That last one matters. A structural suite that matches zero classes is
    worse than no suite, because it produces a green build.

9.4  WHAT RUNS IN CI

    Deptrac, PHPStan, the Pest architecture suite, the unit and
    integration suites, migrations applied to a fresh database and to a
    restored realistic one, and the OpenAPI diff. All of them blocking.

    This is your quality gate for outsourced work. It is also the reason
    the guardrails are worth setting up before the first module rather
    than after the tenth.

PART 10 - TESTING
===============================================================================

    Design Part 6 holds unchanged. The Laravel specifics:

    UNIT TESTS (Level 1)
        Pure PHPUnit/Pest, no Laravel test case, no application boot,
        because the domain has no framework in it. These are fast enough
        to run on save.

    USE CASE TESTS (Level 2)
        Handler plus in-memory fakes for its ports. Still no database.
        Skip this level when the handler is only load-change-save; the
        integration test proves more for barely more time.

    MODULE INTEGRATION TESTS (Level 3) - the centre of gravity
        Real PostgreSQL, real in-process bus, only external providers
        faked. Exercise the module through its HTTP route or its contract.
        Assert on the response, on the database, and on published events.
        Isolation: a transaction rolled back per test, or a fresh schema
        per test class. Never a database that accumulates state between
        tests - that is what makes people stop trusting a suite.
        One suite per module, declared in phpunit.xml pointing at
        `modules/*/tests`, so a module's test dependencies stay visible.

    SYSTEM TESTS (Level 4)
        Deliberately few. Their unique job is proving that an event
        published by one module is received and acted on by another,
        including the outbox round trip.

    GUARD TESTS (Level 5)
        Part 9 above.

    ONE LARAVEL-SPECIFIC WARNING
        Laravel's testing helpers make it easy to assert on framework
        internals - that a job was dispatched, that an event fired, that a
        model exists. Prefer asserting on observable outcomes: the HTTP
        response, the rows in the database, the effect in the other
        module. Tests coupled to framework internals are the ones that
        break when you refactor and teach people that refactoring is
        dangerous.


===============================================================================
PART 11 - FORBIDDEN, AND WHY
===============================================================================

    Each of these is normal, idiomatic Laravel. Each one breaks a rule we
    decided to keep. This is the cost of the framework choice, stated
    plainly so nobody has to rediscover it.

    ┌────────────────────────────────┬──────────────────────────────────┐
    │ Forbidden                      │ Because                          │
    ├────────────────────────────────┼──────────────────────────────────┤
    │ Models outside Infrastructure  │ Persistence leaks into every     │
    │                                │ layer; the table can no longer   │
    │                                │ change independently             │
    │ Eloquent relations across      │ It is a cross-schema join, and   │
    │ modules                        │ it dies at extraction            │
    │ Route model binding            │ Puts a persistence type in the   │
    │                                │ HTTP layer                       │
    │ DB:: or query builder against  │ Breaks single ownership. Also    │
    │ another module's tables        │ fails on the DB role, by design   │
    │ Facades or helpers in Domain   │ Invisible dependencies; untest-  │
    │ or Application                 │ able without the framework       │
    │ now() in domain logic          │ Tests that fail at midnight      │
    │ ->foreign() across schemas     │ Couples deploys and maintenance  │
    │                                │ windows between modules          │
    │ renameColumn on a live table   │ Old code plus new schema during   │
    │                                │ a rolling deploy = breakage      │
    │ A global `app/Models` folder   │ Unowned data, and every module   │
    │                                │ ends up depending on it          │
    │ Observers/global scopes that   │ Action at a distance across a    │
    │ touch other modules            │ boundary, impossible to trace    │
    │ paginate() on growing lists    │ Offset paging: cost grows with   │
    │                                │ page number, rows skip and       │
    │                                │ duplicate under concurrency      │
    │ Business rules in FormRequests │ Not enforced when the module is  │
    │ only                           │ called through its contract      │
    │ A module calling another        │ Use the contract; HTTP is for    │
    │ module's HTTP endpoint         │ outside callers                  │
    └────────────────────────────────┴──────────────────────────────────┘

    If one of these ever looks like the only reasonable answer, that is a
    signal about the boundaries, not permission. Raise it and change the
    design deliberately.


===============================================================================
PART 12 - SETUP ORDER
===============================================================================

    Do these before the first module. Every one of them is cheap now and
    expensive to retrofit.

     1. Fresh Laravel application. Strip the default scaffolding you will
        not use.
     2. PostgreSQL running. Run the bootstrap SQL from design 3.3:
        `platform` and `reporting` schemas, revoke create on `public`,
        owner and app roles.
     3. `packages/shared` and `packages/platform` as Composer path
        packages. Shared gets Money, Currency, Ids, Clock, Result.
     4. Problem-details exception handling, so the very first endpoint
        already returns the standard error shape.
     5. Middleware: correlation id, idempotency key, rate limiting.
     6. Deptrac installed, configured, and failing the build. Prove it
        fails by deliberately writing a violation, then delete it.
     7. PHPStan installed at a high level and green.
     8. Pest, with the architecture suite and the discovery guard test.
     9. CI running all of the above, plus a migration rehearsal.
    10. A module skeleton you can copy - two packages, the folder shape,
        a service provider, a connection entry, two test suites. Creating
        a module should take twenty minutes. A module that takes a day to
        create properly is a module people will avoid creating properly.
    11. The outbox table and its worker.
    12. Only now: the first module, and its thinnest possible vertical
        slice - one endpoint, one handler, one table, one migration, one
        integration test. Something you can call and see a row appear.

    Steps 1 to 11 are perhaps a week of work and they are the difference
    between this architecture existing and this architecture being a
    document. Do not skip ahead to step 12 with the intention of coming
    back. Nobody ever comes back.
